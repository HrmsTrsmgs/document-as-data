# 日付選択Content Controlの表示書式：対応整理

この文書は、日付を書き込んだときの表示書式について、実装・テスト・未確認事項を整理した開発用の検討資料です。
一覧に載せた項目をすべて実装するという決定ではありません。対応範囲とテストは一件ずつ確認します。

## 結論

* 完成した書式文字列を一つずつ列挙するのではなく、基本の7系統と共通の解釈ルールで整理します。
* 同じ記号でも、一文字だけの書式、地域設定、暦、繰り返し方で.NETと結果が異なるため、単純な大小文字変換だけでは全体の互換性を確保できません。
* 現在、表示文字列をテストしている書式は8種類です。基本7系統すべてを確認できた状態ではありません。
* Word独自拡張は別枠で扱います。フィールド用の拡張仕様に載っていることと、現在のWordの日付選択Content Controlで確認できていることを区別します。
* この一覧の行数は、必要なテスト数や残りのRGR回数ではありません。

## 根拠と対象範囲

OOXMLの`w:dateFormat`は、日時表示書式の規定（17.16.4.1）を参照しています。
`MM-YYYY`はその説明に載っている例であり、Wordの既定の表示形式を意味しません。
Wordの既定形式は利用環境の設定に依存します。[OOXMLのdateFormat](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.dateformat?view=openxml-3.0.1)、[WordのDateDisplayFormat](https://learn.microsoft.com/en-us/office/vba/api/word.contentcontrol.datedisplayformat)

今回の対象は、`DatePicker.SelectedDateTime`の設定時に保存する表示文字列です。
`fullDate`の読み取り・時差保持、未入力のコントロールへの初回書き込み、表示内容が複数のrunに分かれる問題は、書式記号とは別の論点です。
既に決定した`DateTimeOffset`による読み書きの方針は変更しません。

## 現在の実装とテスト

確認対象：[DatePicker.cs](../src/DocumentAsData/DatePicker.cs)、[DatePickerのテスト.cs](../tests/DocumentAsData.Tests/DatePickerのテスト.cs)。

| 書式 | 設定する日時の日付部分 | 検証している表示文字列 | 確認対象 |
|---|---|---|---|
| `yyyy/MM/dd` | 2026-12-31 | `2026/12/31` | 小文字の年・数値の月日 |
| `MM-YYYY` | 2026-12-31 | `12-2026` | 大文字の四桁年 |
| `'YYYY' YYYY/MM/dd` | 2026-12-31 | `YYYY 2026/12/31` | 引用部分を保持し、外側だけ年へ変換 |
| `yy`、`YY` | 2006-12-31 | `06` | 小文字・大文字の二桁年とゼロ埋め |
| `YYYY/MM/DD` | 2026-12-31 | `2026/12/31` | 大文字の日指定 |
| `DDD` | 2026-12-31 | `Thu` | 大文字の曜日略称（英語） |
| `DDDD` | 2026-12-31 | `Thursday` | 大文字の曜日正式名称（英語） |

固定DOCXの表示言語は曜日指定の2件が`en-US`、ほかは`ja-JP`で、暦はいずれも`gregorian`です。
入力DOCXを`validate: true`で開き、保存後の`w:t`を検証しています。
Word実機での表示確認ではなく、引用文字列・大文字年・二桁年・大文字の日や曜日指定の追加ファイルは仕様を狙って作ったOOXMLです。
XMLの構造検証だけで、Wordとの表示互換性まで確認できるわけではありません。

現実装は、単一引用符で囲んだ部分を保護して`Y`や`D`の連続を小文字化し、それ以外の書式を.NETの`DateTimeOffset.ToString`へ渡します。
したがって、下記の未確認記号をすべて正しく扱う実装でも、非対応として拒否する実装でもありません。

## 1. 基本の7系統

ここでいう「基本」はWordの利用者向け説明に基づく分類であり、OOXML規格の全項目数を意味しません。
Word側の意味は[基本書式の公式説明](https://support.microsoft.com/en-us/word/format-field-results)、.NET側は[カスタム日時書式](https://learn.microsoft.com/en-us/dotnet/standard/base-types/custom-date-and-time-format-strings)を比較しています。
以下の「共通」は書式の意味が対応するという意味で、全入力・全地域でテスト済みという意味ではありません。

| 系統 | Word側の記号 | .NETとの関係・注意点 | 現在の確認範囲 |
|---|---|---|---|
| 年 | `yy`、`yyyy`、`YY`、`YYYY` | 小文字は対応。大文字は変換が必要。単独の`y`や長い繰り返しは別途検討 | 上記6書式で二桁・四桁の年を確認 |
| 月 | `M`、`MM`、`MMM`、`MMMM` | 数値・略称・月名の指定は対応。月名は言語に依存 | `MM`のみ。略称・月名・一桁月は未確認 |
| 日・曜日 | `d`、`dd`、`ddd`、`dddd`と大文字版 | 小文字は対応。大文字版はそのまま.NETへ渡せない | `dd`と`DD`、英語の`DDD`と`DDDD`を確認 |
| 時 | `h`、`hh`、`H`、`HH` | 12時間・24時間の区別は対応 | 表示としては未確認 |
| 分 | `m`、`mm` | 対応。ただし月の`M`と区別する | 表示としては未確認 |
| 秒 | `s`、`ss` | 対応。大文字版の拡張は別枠 | 表示としては未確認 |
| 午前・午後 | `am/pm`、`AM/PM` | .NETの対応記号は`tt`。単純な文字列扱いでは表示を壊す | 未対応・未テスト |

たとえば`yyyy-MM-dd`と`dd/MM/yyyy`の順序違いごとに専用処理を増やす必要はありません。
同じ記号の意味を組み合わせて扱えることを、読みやすい代表例で確認する方針が適切です。

## 2. 書式全体に関わるルール

| 論点 | 現状と差異 | 次に確認する観点 |
|---|---|---|
| 引用文字列 | 単一引用符の基本例はテスト済み | 引用符そのもの、二重引用符、バックスラッシュの解釈は未確認。.NETのエスケープ規則をWordの規則と同一視しない |
| 区切り文字 | .NETの`/`と`:`は地域別の区切り文字になる。Wordの記号をそのまま残す処理とは同じではない | 指定したスラッシュやコロンと、地域設定上の区切り文字が異なる例 |
| 一文字だけの書式 | .NETは`d`などをカスタム書式ではなく標準書式として解釈する | 日だけ、月だけ、時だけを指定した場合。複合書式の一部として動くことでは代替できない |
| 記号の繰り返し | Word拡張には長い連続を複数の記号へ分けて表示する規則がある | `yyy`などを.NETへそのまま渡してよいか。単純な`Y`の小文字化で解決したとはしない |
| 表示言語 | 実装は`w:lid`を.NETのカルチャーとして使用 | 月名・曜日名・午前午後の表示。現在の数値だけの`ja-JP`テストでは確認できない |
| 表示設定の省略 | 実装は`dateFormat`と`lid`の存在を要求するが、OOXMLには省略時の規定がある | 形式・言語それぞれの省略と、その参照先。ローカルPCの現在設定で適当に補わない |
| 暦 | 実装は`w:calendar`を表示処理に使っていない | UI用の暦指定と表示書式・言語との関係。`calendar`があるだけで年の変換方法を断定しない |
| その他の文字・未対応記号 | .NET側だけで特別な意味を持つ文字もある。現在は非対応を検出しない | 文字として残すものと解釈する記号を区別する。非対応時の例外・無変更などの扱いは未決定 |

一文字書式・区切り文字・エスケープの違いは[.NETの公式説明](https://learn.microsoft.com/en-us/dotnet/standard/base-types/custom-date-and-time-format-strings#notes)との比較です。
Word側の文字列と区切り文字の説明は[基本書式](https://support.microsoft.com/en-us/word/format-field-results)、繰り返し規則は[Wordの拡張仕様](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/e03ea6ec-7739-461f-ba7f-d11e2058e818)を参照しています。
まだ新しい固定DOCXによる再現テストは作成していません。

設定の省略は不正XMLとは限りません。`dateFormat`の省略時は言語に基づく標準形式、`lid`の省略時は内容のrunの言語、`calendar`の省略時はグレゴリオ暦が規定されています。
ただし、`calendar`の説明は日付選択UIの暦を対象としており、その説明だけで保存する表示文字列の暦まで決定しません。[dateFormat](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.dateformat?view=openxml-3.0.1)、[lid](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.languageid?view=openxml-3.0.1)、[calendar](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.calendar?view=openxml-3.0.1)

## 3. Word独自拡張：対応範囲の検討が必要なもの

以下は[MS-OE376の日時書式に関するWord拡張](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/e03ea6ec-7739-461f-ba7f-d11e2058e818)に記載される記号を、責務別に整理したものです。
同資料には旧製品への適用注記やフィールド専用のスイッチも含まれます。
この表は現行Wordの日付選択Content Controlでの対応一覧ではなく、実機確認前の調査対象です。

| 分類 | 記号の例 | 検討内容 |
|---|---|---|
| 元号・暦上の年 | `e`、`ee`、`n`、`nn`、`E`、`EE`、`g`、`gg`、`ggg`、`G`、`GG` | 和暦年、元号名、その略称。言語で意味が異なるものがあり、単純に.NETの`g`や`y`へ置換できない |
| 地域別の曜日表現 | `aaa`、`w`、`W` | 日本語などでの曜日表示と、他言語で文字列として扱う場合 |
| 漢数字・地域別の時刻表現 | `A`、`O`、`C`、`I`、`r`、`rr`、`R`、`RR` | 月・日・時・分・秒の数字や時刻表現。言語との組み合わせが必要 |
| 仏暦・タイ語の記号 | `bb`、`bbbb`、`ว`系、`ด`系、`ปป`、`ปปปป` | 他の記号の暦にも影響する指定があり、独立した文字置換では足りない |
| 追加の綴り | `BB`、`BBBB`、`y`、`Y`、`S`、`SS`、`AMPM`、`PMAM`、`JAM/JPM`、`JPM/JAM` | 基本記号との関係、言語依存、単独・繰り返し時の意味 |

これらの互換性を確認する専用テストはありません。日本語の文書が対象でも、数値の西暦日付と和暦・漢数字では必要な対応が異なります。
日付選択Content Controlでの受理、保存される`dateFormat`、Wordによる表示更新を確認してから、対象にするか判断します。

また、Wordのフィールド書式には、バッククォートで囲んだ連番項目を参照する説明があります。
文書内の別項目へ依存するため通常の日時変換とは責務が異なり、日付選択Content Controlでも必要かは未確認です。
フィールドの`\h`・`\s`などのスイッチも、`w:dateFormat`へそのまま持ち込むとは決めません。[Wordの書式説明](https://support.microsoft.com/en-us/word/format-field-results)

## 保留中のテストと再開方針

基本書式と共通ルールを、既存の`DatePickerのテスト`内に16件のSkip付き仕様メモとして残しています。
二桁年のメモは固定DOCXを使う2ケースのTheoryとして有効化し、既存実装で成功しました。
大文字の日指定は`YYYY/MM/DD`の表示が`2026/12/DD`になるRedを確認し、`D`の変換を追加してGreenにしました。
大文字の曜日指定は英語の略称・正式名称を2ケースのTheoryとして有効化し、既存実装で成功しました。
日付書式の確認を一件ずつ再開しています。全体の0.3.0への採用範囲は未決定です。

Skipテストには確認事項をコメントとして記載し、本文は`NotImplementedException`に留めています。
固定DOCXとアサーションはまだ用意していません。Skipを外すだけで仕様のRedになるものではありません。
再開時に仕様・期待値をレビューし、固定DOCXと検証コードを準備してからRedを確認します。
和暦などの独自拡張は、下記の対応範囲を決めるまでは資料上の候補に留めます。

まず基本の7系統と、その利用に必要な共通ルールを対象候補とします。独自拡張をまとめて実装する計画にはしません。

1. 基本記号の既知の差を確認する。大文字の日・曜日指定は確認済みで、次の候補は一桁の月日でのゼロ埋め。
2. 午前・午後、一文字書式、区切り文字を、それぞれ別の振る舞いとして確認する。
3. 小文字の月名・曜日・時分秒など、.NETと意味が共通の部分を代表例で確認する。最初からGreenでも、不必要な実装を追加しない。
4. 引用・その他の文字・繰り返し・設定省略を精査する。仕様が曖昧なものはWordで確認してからテスト化する。
5. 和暦などの拡張と、対応できない書式の扱いを決める。黙って誤表示してよいという仕様にはしないが、拒否APIをこの整理だけで追加もしない。

テストは文書の公開APIから値を設定し、保存後の表示文字列を観測します。
固定DOCXには確認する書式・言語・暦が分かる名前とコメントを付けます。
書式変換用のprivateメソッドを公開したり、完成した書式の組み合わせを総当たりにしたりはしません。

当初の保留作業ではSkipメモだけを追加しました。再開後の確認範囲と実装は上記のとおりです。
