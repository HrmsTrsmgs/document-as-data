## 読み方と更新方法

* まず「現在の作業状態」を読み、次に必要な判断の「仕様・制約」と「未確定事項」を確認します。
* 仕様が不明な場合は、実装を推測で進めず、必要な範囲だけ開発者へ質問します。
* 確定した判断だけを「仕様・制約」または「設計判断」に追加します。
* 採用しなかった案は、将来も同じ議論を繰り返す可能性がある場合だけ「却下した案」に記録します。
* 事実、AIによる推測、未確認事項を見出しまたはラベルで区別します。
* 作業を中断するときは「現在の作業状態」の未完了事項と次の着手点だけを更新します。

## 仕様・制約（確認済み）

* DocumentAsDataは、名前付きの構造を持つDOCXを構造化データとして読み書きするライブラリです。自由入力文書から意味を推測する機能は対象外です。詳細は[README](../README.md)と[機能リファレンス](reference.md)を参照してください。
* 初期の公開概念では、MERGEFIELDとContent Controlを統合せず、別コレクションとして扱います。
* Open XML SDKの型や複雑なOOXML構造は、原則として公開APIへ露出させません。
* PDF化、レイアウト計算、OCR、自然言語解析、Content Controlの除去・アンラップは責務に含めません。
* コード生成はテンプレートの名前付き項目と強く結び付きます。生成型の検証や、通常項目と繰り返し明細の検索範囲には既知の制約があります。実装済みの範囲は[機能リファレンス](reference.md)とコード生成テストを参照してください。
* Stream入出力では、入力Streamをライブラリが閉じず、`SaveAs(Stream)`は別のシーク可能な出力先へ文書全体を書き込みます。詳細な契約は[機能リファレンス](reference.md)を参照してください。

## 設計判断（理由）

| 判断 | 理由 | 正本・根拠 |
| --- | --- | --- |
| 名前を`WordAsData`ではなく`DocumentAsData`とする | 将来のODT等の可能性を残しつつ、初期実装はDOCXへ限定するため | [設計文書](design-v0.1.md)、README |
| MERGEFIELDとContent Controlを別概念として公開する | プログラムから差し込む項目と、人間との双方向入力項目では意味とライフサイクルが異なるため | README、Coreテスト |
| データ項目にはWord側で明示的な名前付き構造を要求する | 段落番号・ページ番号などは安定した識別子にならず、自由文解析は責務外のため | README、機能リファレンス |
| 既存のTDD工程別コンテキストを維持し、AI-DLCは記録と再開補助に限定する | 開発手順を置き換えず、仕様判断の継続性だけを補うため | `docs/ai-instructions/tdd-context/` |

## 却下した案

* **共通の`Document.Fields`抽象化**：MERGEFIELDとContent Controlの意味を初期段階で消すため、実際の共通価値が確認できるまで導入しません。
* **Word文書を通常のテキストへ変換して扱う**：フィールドやContent Controlの構造を維持する責務と両立しないため対象外です。
* **PDF化やWordの自動操作をライブラリへ含める**：レイアウト計算や外部アプリ操作は利用側の責務とするため対象外です。
* **段落・ページ・行番号による主識別**：文書編集で安定しないため採用しません。
