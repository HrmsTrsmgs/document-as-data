# C#/.NET開発指示

この文書は、C#、.NET、xUnit、FluentAssertions、NuGet、MSBuildを扱う作業に適用する。

## C#コード記述

* C#の明示的な記述は、設計意図、境界、制約を読む助けになる場合に残す。
* 言語仕様上の既定値、型推論で明白な型、同じ情報の重複は書かない。
* 明示しなくても `private` になるメンバーに `private` を書かない。
* ラムダで、引数名に固有の意味を持たせない場合は `it` とする。
* `_` は未使用引数または discard に限定し、参照する値の名前として使わない。
* 拡張メソッドの `this` 引数は `self` とする。
* 拡張メソッドは、利用できる場合は C# の拡張ブロック構文 `extension(T self)` を使う。
* 拡張ブロックのレシーバー名も `self` とする。
* 値を返すだけの短いメソッド、プロパティ、インデクサーは、読みやすさを損なわない範囲で式形式を使う。
* 複数行に分ける場合も、単に次の呼び出しへ渡すだけの一時変数は作らない。
* 一時変数を、値を受けるだけの目的で不用意に増やさない。
* 添字、位置、分割結果などの機械的な値は、意味が読み取れる名前に置き換えられる場合に一時変数を使用する。
* 日本語の仕様語彙や業務概念を英語名へ置き換えることで意味が曖昧になる場合は、一時変数を増やす効果を慎重に判断する。
* テストコードでは、日本語識別子の方が仕様として読みやすい場合は日本語識別子を使用してよい。
* 標準ライブラリや言語機能は、短く書くためだけではなく、その機能が表す意味に合わせて選ぶ。

## LINQと取得演算子

* LINQは、メソッド構文のほうが可読性が明確に高い場合を除き、クエリ構文を使う。
* 単純な集約、変換APIへの直接接続、FluentAssertionsへつなぐ検証など、メソッド構文のほうが読みやすい場合はメソッド構文を使う。
* LINQクエリ構文で `from ... in` の右辺が複数行になる場合は、`in` の後で改行し、右辺全体の範囲が分かるようにインデントする。
* LINQの取得演算子は、例外を出す手段ではなく、対象データに期待する件数や順序の意味を表すために選ぶ。
* `Single` は一致がちょうど1件である不変条件を表す場合に使う。
* `SingleOrDefault` は0件を通常の分岐として扱い、複数件を前提違反として扱う場合に使う。
* `First` と `FirstOrDefault` は、複数件の一意性を要求しない場合に使う。
* 標準APIが自然に投げる例外を、そのまま公開APIの仕様として扱うかどうかは、テストで固定する対象になった時点で判断する。

## dynamic、キャスト、null許容

* `dynamic` へ切り替える必要がある場合は、式中に `(dynamic)` を残さず、一時変数で境界を明示する。
* `dynamic` 経由で生成メンバーへアクセスするテストでは、`bookAccessor` など対象とアクセス用途が分かる名前を使う。
* `dynamic` の結果を既知の型として扱う場合は、代入先の型を明示して受ける。
* 明示キャストが式を読みにくくする場合は、可能なら `as` を使って一時変数へ受ける。
* 値型など `as` が使えない場合は、明示型代入または必要最小限のキャストに留める。
* Null許容警告や型検査を通すために `!` で事実を作らない。
* `!` は、コード上の不変条件が明確で、読み手にもその理由が追える場合に限る。

## XMLコメント

* XMLコメントは、IntelliSenseとAPI参照で読む人を助けるために書く。
* `public` メンバーのコメントは、ライブラリ使用者向けに書く。
* `public` メンバーでは、外部から見た役割、引数、戻り値、例外、利用時に知るべき振る舞いを説明する。
* `internal` と `private` メンバーのコメントは、コードリーディング向けに書く。
* `internal` と `private` メンバーでは、実装上の意図、保持する状態の意味、不変条件、キャッシュ、遅延生成、低水準APIの扱いを説明する。
* 名前や型を言い換えるだけのコメントは避け、コードを読む判断材料になる内容を書く。
* コメントは丁寧に書くが、実装より詳しすぎる説明や、変更時に陳腐化しやすい説明は避ける。
* 振る舞いや制約を変更した場合は、対応するXMLコメントも更新する。

## テスト記述

* テストコードのローカル変数と一時変数の詳細方針は `docs/testing-style.md` を参照する。
* 既存のテストフレームワークと命名規則を優先する。
* テスト名は、既存方針と整合する場合は日本語文にする。
* テスト名から、対象の振る舞いと期待結果が読み取れるようにする。
* 一つのテストは、レビュー時に一つの仕様として読める粒度にする。
* テスト補助APIやテストDSLの名前は、テストから何を観測しているかが読み取れることを優先する。
* テスト補助APIやテストDSLの命名を変える場合は、まず一つのテストで変更例を示し、読みやすさを確認してから同種のテストへ展開する。
* ローカル変数は原則として `var` を使い、型そのものを示す必要がある場合だけ具体型を明記する。
* 一時変数は、評価回数の固定、検証対象の共有、概念境界の明示、デバッグ容易性に意味がある場合に作る。
* 一度しか使わず、右辺の式がそのまま意味を表す `actual`、`result`、`expected` などの一般名変数は作らない。
* テスト対象となるオブジェクトを変数で受ける必要があり、型名や種類名をそのまま変数名にするだけなら `tested` とする。
* 例外検証のラムダも原則として `var` で受け、デリゲート型そのものを示す必要がある場合だけ `Action` や `Func<T>` を明記する。
* 静的型で保証できる戻り値の型を、実行時アサーションで確認しない。
* APIの形として戻り値の型を示したい場合は、`var` ではなく明示的な型の変数で受ける。
* 実装詳細ではなく、外部から観測できる振る舞いを優先してテストする。
* 単体テストと実ファイルを使用するテストを区別する。
* テストを実行順序に依存させない。
* テストを開発者固有の絶対パスに依存させない。
* テスト同士で同じ出力ファイルを共有しない。
* 一時ファイルはテストごとに分離する。
* 一時ファイルは可能な限りテスト終了後に削除する。
* カルチャー、タイムゾーン、現在時刻へ不必要に依存させない。
* 今回のユースケースに関係しないケースを、網羅性だけを目的に追加しない。

## FluentAssertions

* FluentAssertions の `Should().NotBeNull()` は nullable 解析に対応しているため、確認後の同じ変数は非 null として扱える。
* nullable な値を `Should().NotBeNull()` で検証した後、その値を続けて検証するためだけに `!`、`?? throw`、`Which` を追加しない。
* `Which` はFluentAssertionsのチェーンで後続の `Should()` へつなぐ場合に使い、nullable回避の一時変数化には使わない。
* FluentAssertions の `Should()` と最終アサーションは原則として同じ行に置き、`Should()` だけを単独行にしない。
* FluentAssertions の `Which`、検証対象の短いプロパティ、`ToString()` なども、一続きの句として読める場合は無理に縦へ分割しない。
* FluentAssertions のチェーンは、声に出して読んだときの区切りや意味の切れ目で改行してよいが、`Should()` の前で改行すること自体をルールにはしない。

## ビルドと検証

* 作業前に対象ソリューション、プロジェクト、.NETバージョンを確認する。
* `global.json` が存在する場合は、その指定を確認する。
* 実在するソリューションまたはプロジェクトに対してビルドを実行する。
* 実在するテストプロジェクトに対してテストを実行する。
* 存在しないパス、プロジェクト名、コマンドを推測しない。
* パッケージの追加、更新、ダウングレードを、明示的な必要性なく行わない。
* コード変更後は、対象テスト、関連テスト、可能であれば全テストとビルドを実行する。
* C#の調査やリファクタリングでは、まず `dotnet build`、`dotnet test`、`dotnet format`、アナライザ診断などの機械的な結果を利用し、必要な箇所へ検索を絞る。
* コンパイルエラーやテスト失敗が示す型、メンバー、ファイルを起点に確認し、無関係なファイル読み取りでトークンを消費しない。
* ビルド警告が今回の変更によるものか、既存のものか区別する。
* 警告を無条件に抑制しない。
* テスト失敗を、根拠なく今回の変更と無関係だと判断しない。
* 実行できなかった確認項目は理由を報告する。
* テスト成功だけで、設計や生成ファイルの妥当性を保証したと扱わない。
