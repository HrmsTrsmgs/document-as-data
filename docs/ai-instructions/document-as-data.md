# DocumentAsData固有作業指示

この文書は、DocumentAsDataリポジトリに固有の目的、設計、公開準備、周辺運用を定義する。

## プロジェクトの目的

DocumentAsDataを、第三者がビルド、テスト、利用、レビューできるC#/.NETライブラリとして整備する。
Word文書をWordのオブジェクトモデルではなく、名前の付いた構造化データとして読み書きできることを目的とする。

機能数を増やすことより、次を優先する。

* 利用側コードの簡潔さ
* 変更箇所の局所化
* 責務分離
* 依存関係の整理
* Open XML SDKの低水準APIの抽象化
* 公開APIの理解しやすさ
* テスト可能性
* 自動テストによる振る舞いの確認
* READMEから目的、使用方法、制約を理解できること

業務固有の帳票仕様、DTO、データ、推測処理は含めない。

## SpreadsheetAsDataとの関係

* DocumentAsDataはSpreadsheetAsDataと同じ「文書を構造化データとして扱う」発想を引き継ぐ。
* 公開API、コレクション、命名、テスト、文書、パッケージ構成を検討するときは、先にSpreadsheetAsDataの対応する実装と方針を確認する。
* `docs/design-v0.1.md` に記載された公開API案は初期のラフ案であり、実装の参考または仕様として使用しない。
* 公開APIはSpreadsheetAsDataの対応する既存APIとテストを基準とし、一つずつDocumentAsData向けに読み替える。
* SpreadsheetAsDataのAPIや構成から変える場合は、Word固有の理由または新規OSSとして変更する理由を示す。
* SpreadsheetAsDataのコード生成も移植元として確認し、DocumentAsDataの名前付き文書項目に自然に対応する機能を一つずつ読み替える。
* Excelのワークシート、テーブル、行、列などに固有のコード生成機能は機械的に移植しない。
* 利用側へ文書固有の型を生成する汎用機能は、ライブラリ自体へ業務固有のDTOを含めることとは区別する。
* Ruby版など、DocumentAsDataの初期目的にない実装は機械的に移植しない。
* SpreadsheetAsDataの依存バージョンや暫定実装を、妥当性を確認せずコピーしない。

## TDDによる移植手順

* SpreadsheetAsDataの既存テストを一つずつ起点にし、テストが表す利用者視点の振る舞いを確認する。
* その振る舞いにDocumentAsDataとして自然な対応がある場合だけ、Word文書向けのRedテストへ読み替える。
* Excelのセル、範囲、ワークシート、テーブルなどに固有で、DocumentAsDataに対応する概念がないテストは移植しない。
* 対応がない機能のために、DocumentAsData側へ不自然な抽象化や代替APIを作らない。
* 元テストのコードを機械的に置換せず、何を観測するテストかを保った最小のDocumentAsData用テストとして書く。
* 一度に有効にするRedテストは一つ、またはユーザーと合意した小さい仕様のまとまりに限定する。
* 各Redに着手する前に、対応元テスト、DocumentAsDataでの読み替え、移植するか対象外とするかを一件だけ提示し、ユーザーの確認を得る。
* 複数のRedや対応なしと判断した複数テストをまとめて確認しない。
* Redでは、対応元のSpreadsheetAsDataテストと、DocumentAsDataでどう読み替えたかを報告する。
* Redの失敗が意図どおりであることを確認してから、そのRedだけをGreenにする。
* Red確認後にGreenへ進む場合も、ユーザーの確認を得る。Green完了後、次のRedへ自動で進まない。
* Green後に必要な場合だけ、外部から観測できる振る舞いを変えずにRefactorする。
* 一つのRed、Green、Refactorが完了してから、次に読むSpreadsheetAsDataテストを選ぶ。
* 将来分の公開API案やSkipテストを先にまとめて追加しない。複数の仕様を同時にレビューするようユーザーが明示した場合だけ例外とする。
* 複数の仕様テストを先に追加する場合も、Skipを含む全テストが常にコンパイルできる状態を保つ。
* Skipテストのコンパイルに必要な公開APIは最小スタブとして追加し、未着手の振る舞いは原則として `NotImplementedException` を投げる。
* 未着手のAPIへ空コレクション、既定値、仮の成功値を返し、将来のテストを意図せずGreenにしない。

## 設計と公開API

* `docs/design-v0.1.md` は目的と対象範囲の確認にのみ使用し、同文書の公開API案を参照しない。
* 初期バージョンでは `MergeFields` と `ContentControls` を別々の概念として公開し、共通の `Fields` 抽象化を作らない。
* Open XML SDK固有の型を公開APIへ原則として露出させない。
* MERGEFIELDとContent Controlの意味やライフサイクルの違いを内部都合で消さない。
* 文書内の主要なデータ識別方法として、段落番号、表番号、ページ番号、行番号を導入しない。
* 公開API、依存パッケージ、ビルド構成、保存方法を変更する前に、理由と影響範囲を確認する。
* 公開API案は、可能な限りRed段階の利用側テストとして提示し、名前と使用感をレビューできる形にする。
* テストのためだけに型やメンバーの公開範囲を広げない。
* v0.1では、将来のODT対応を理由に過剰な抽象化を追加しない。

## 初期対象

* DOCXを開く。
* 本文のMERGEFIELDを列挙し、名前で検索して値を書き込む。
* simple fieldと、Wordが通常生成する複合フィールドを扱う。
* 本文のContent Controlを列挙し、Tagで検索して値を読み書きする。
* 同名項目が複数ある場合の振る舞いは、実装前にテストで明示する。
* 編集結果を別のDOCXファイルとして保存する。
* 本文内の基本ケースから始め、表、ヘッダー、フッター、ネストは個別のGreen対象として段階的に扱う。

## 対象外

* PDFレンダリングとレイアウト計算
* Content Controlの除去またはアンラップ
* MERGEFIELDの通常テキスト化
* 文書レイアウト編集
* OCR、自然言語解析、自由入力文書からの推測抽出
* WordやLibreOfficeの自動操作

対象外機能を、補助機能として先回りして追加しない。

## Open XML SDKとDOCX

* SDKのAPI、型、要素構造、保存動作を記憶だけで推測しない。
* 使用するSDKバージョンとAPIは、公式資料、参照中のパッケージ、コンパイラ、IDEまたは実行結果で確認する。
* コンパイル成功だけで生成DOCXが妥当だと判断しない。
* 保存後のDOCXを再度開き、値、フィールド構造、Content Control、Tagが保持されることを確認する。
* 必要な段階でOpen XML Validatorを使用する。
* 不明な既存要素、書式、run、プロパティを無条件に削除または再生成しない。
* ファイル、ストリーム、WordprocessingDocumentの所有権、破棄、保存タイミングをテストで確認する。

## テストデータ

* テストDOCXは、テストの意図が読み取れる最小限の内容にする。
* オールインワンの巨大なDOCXで無関係な仕様をまとめて確認しない。
* プログラム生成するDOCXと、実際のWordが生成したDOCXの役割を区別する。
* XML構造だけを狙うテストには最小ビルダーを使用してよい。
* Word固有の生成差異を確認するケースでは、出所と確認対象が分かる固定テストデータを使用する。
* Wordで開いて保存しただけのOOXMLノイズを、仕様差分と取り違えない。
* バイナリ差分をコミットする前に、追加理由、サイズ、含まれるデータを確認する。

## READMEと公開準備

* READMEには、実装とテストから確認できる内容だけを書く。
* 未実装機能を実装済みのように書かない。
* READMEは、初めて使う人が目的と最小利用例を先に理解できる順にする。
* Open XML SDKを直接扱う場合との差が分かるようにする。
* NuGetパッケージ、APIドキュメント、サンプルは、中心APIがGreenになってから個別の作業単位として整備する。
* APIキーや公開用トークンは出力、保存、コミットしない。

## テキストファイルの正規化

* `apply_patch` などでテキストファイルを編集した作業単位ごとに、`scripts/Normalize-ChangedTextFiles.ps1 -IncludeUntracked` を実行する。
* 正規化をコミット直前まで遅らせず、Visual Studioで編集結果を確認する前に改行コードとBOMの混在を解消する。

* コミット前に `scripts/Normalize-ChangedTextFiles.ps1 -IncludeUntracked` を実行し、変更中のテキストファイルの改行コードとBOMを機械的に正規化する。
* 正規化後に差分を再確認する。
* バイナリファイルなど正規化対象外のファイルは、サイズと目的を確認してからコミット対象に含める。
