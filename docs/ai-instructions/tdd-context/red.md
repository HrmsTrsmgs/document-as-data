# Red: 利用側から外部契約を決める

`common.md` とこの文書だけを工程指示として読む。Redは失敗テストを作るだけでなく、
責務、呼び出し、入力、戻り値、外から見える状態変化を利用側から設計する。

今回の未充足の振る舞いを一つ選び、責務、呼び出し方、入力、戻り値、外部から見える
状態変化を利用者側から設計する。実装の容易さや完成形の内部構造からAPIを逆算しない。
既に確定した契約は設計し直さない。

対象機能、同じドメインオブジェクト、同じ公開境界、類似ユースケース、代表的な呼び出し側、
互換性に関わる既存テスト・API利用例を検索して、必要なものだけ読む。
既存テストは現行契約、互換性、旧仕様、意味未確認を根拠に応じて区別する。
対象実装の内部アルゴリズムやGreen・Refactorの履歴は原則として参照しない。
確定済みの契約を毎回設計し直さず、次の未充足の振る舞いを一件選ぶ。
全件のテスト計画や完成形の実装計画を先に確定しない。

利用者としての使用例をテストに書き、そのcall siteを読み直す。
名前と引数の意味・順序が伝わるか、booleanや文字列の意味を不必要に推測させないか、
内部都合や不要な状態管理を利用者へ押し付けていないか、既存の類似APIと整合するかを確認する。
「可読性を考慮した」という報告より、実際の呼び出しコードを判断対象にする。

期待値は要求と確定契約から決め、現在の実装結果を写さない。
テストを実行し、意図した理由で失敗するか確認する。APIが未存在なら、実行に必要な
宣言や `NotImplementedException` スタブだけを追加してよい。環境障害と仕様上の失敗を区別する。
最初から正しく通る場合は実装を壊さない。Skipで保留する場合は理由と解除条件を明記する。

本プロジェクトで合意済みの将来観点をまとめて記録する場合は、既存テストとの重複を確認し、
理由と解除条件が分かる `Skip` を付ける。未合意の将来仕様を先取りして増やさない。

成果物はテスト、必要なAPI宣言、確定契約、実行結果。
進行役には場所・識別子・失敗結果・契約だけを短く返す。
Greenの実装を始めず、通常経路に新しいAI設計承認を求めない。
