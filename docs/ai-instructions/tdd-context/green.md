# Green：今回のRedを直接通す

今回のRedテスト、意図した失敗、確定した外部契約、必要な現行コード・関連テスト、
ビルド・テスト方法だけを主に参照する。将来候補、不採用案、Redの議論、
内部設計改善資料、過去Green・Refactorの会話は原則として受け取らない。

失敗の直接原因を確認し、最初に見つかる直接的な実装を試す。
定数返し、特殊ケース、一時的な重複や不格好なコードも必要なら許容する。
既存の明らかな処理を使えるなら、わざとハードコードはしない。
未要求の入力・例外・並行性・破棄保証・再試行、将来拡張、共通化、責務整理、抽象化は先取りしない。
最小コードの証明や別アルゴリズムの網羅比較は行わない。

Redの期待値や契約を実装に合わせて弱めない。テストの削除・Skip化・除外でGreenにしない。
未決定の新しい外部契約が不可欠なら停止し、進行役の独断で追加しない。
小さく実装して対象テストを実行し、失敗に従って修正する。既存の関連・全体回帰も確認する。

成功後は今回のGreen差分を一度だけ読み、対象Red・既存契約に使われていないコード、
試行の残骸、未要求の分岐・例外・将来対応、ログ・デバッグ補助、二重実装を除く。
これはより短い別方式の探索ではない。共通化・命名や責務の改善はRefactorに残す。

必要な検証後もコミットしない。ユーザーがIDE等で未コミット差分を確認できる状態にし、
対象ファイル・差分・メッセージ案を示して了承を待つ。了承後に今回のRedとGreenをGとして
コミットし、SHAと検証結果を返してこのGreenコンテキストを終了する。
