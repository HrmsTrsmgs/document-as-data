# 工程別TDDの入口・進行役

進行役は別コンテキストの起動と成果物の一方向の受け渡しだけを行う。
設計の再審査、差分の意味レビュー、新しい仕様の追加、テスト成功の再確認はしない。

## 起動と再開

このCodex環境では `spawn_agent` の `fork_turns: "none"` で親の会話履歴を渡さず、
工程ごとの担当を起動できる。起動文には要求・確定契約・作業ツリー・成果物の参照先と、
`common.md` および担当工程の文書を読む指示だけを含める。担当には他工程への相談や
子エージェント作成を指示しない。同じ担当の継続には `followup_task` を使える。
これらは現在のツールで確認できた方法であり、将来ツールが異なる場合は再確認する。

同じ作業の続きは既存の作業ツリーとGit・テスト成果物から再開する。
工程分割のためにworktreeを作り直さない。Skillを分けたり、同じチャットで役割を
切り替えたりしただけでは別コンテキストにならない。別コンテキストの起動手段が
使えなければ、分離済みと報告せずユーザーへ制約を伝える。
既存の未コミット差分が前サイクルのGreen等であれば、その人間レビュー境界から再開する。
帰属が不明な差分を新しいG/Fコミットへ混ぜない。

Redは同じ外部契約の設計中なら継続してよい。Greenは原則としてRedサイクルごとに
新規担当とし、同じRedの失敗修正だけ継続する。Refactorは同じ設計領域なら継続してよい。
古い履歴が必要な版や契約を特定できなくなったときは、現行成果物から新規に構築する。
モデル選択は [models.md](models.md) に分離し、工程へ選択理由の長文を渡さない。

## 通常の順序

Red → Green → ユーザーの未コミット差分確認 → Gコミット → Refactor →
実変更があればユーザーの未コミット差分確認 → Fコミット → 次のRed。
Refactorに変更がなければFコミットを作らず、Gを最終基準とする。空コミットは禁止する。
Redテストが最初から正しく通る場合は実装を壊してRedにせず、既存方針に従って扱う。
ユーザーが「Redまで」「Greenまで」などの停止点を指定した場合はそこで止まる。

## 渡す情報

* Redへ：元の要求、利用場面、確定済み契約、既知の互換性制約、既存API・テストを探索できる参照先。未決定のAPIや完成形の実装案を進行役が先に決めない。
* Greenへ：今回のRedテストの場所と識別子、意図した失敗結果、確定した契約、必要な現行コード・関連テストの参照先、ビルド・テスト方法、必須制約。Redの比較履歴、将来候補、不採用案、Refactor方針は渡さない。
* Refactorへ：GのSHA、対象設計領域、現行コード・テスト・契約の参照先、必要な設計・品質規約。継続担当には最後の同期SHAも渡す。Greenの思考履歴は渡さない。

担当が現在の契約で進められない場合は、その理由と必要な判断だけをユーザーへ示す。
進行役が仕様を足して同じGreenへ差し戻さない。契約を修正した場合は新しいGreenを起動する。
担当の検証完了後に進行役が追加のAIレビューを挟まない。人間レビューと既存の安全規則は維持する。
